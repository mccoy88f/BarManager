# BarManager — Documento di Sviluppo

> Piattaforma **multi-tenant** (un sotto-dominio per locale) per la gestione operativa di bar/ristoranti: presenze dipendenti, controlli HACCP, inventario e ordini fornitori, menù online, attività e scadenze — con una home dell'amministrazione che riepiloga ciò che richiede attenzione ogni giorno. Web app installabile come PWA, progettata per essere convertita in app Android nativa (wrapper Capacitor) senza riscrivere il frontend. Pensata per il deploy su **Portainer** o **Coolify**, dietro il loro reverse proxy.

Versione: 0.5 — Fase 1 rifinitura MVP completata (UI amministrazione, rate limiting, test, CI)
Data: 2026-09-21

---

## 1. Obiettivi e principi guida

- **Multi-tenant fin dall'inizio**: un'unica installazione serve N locali, ciascuno isolato per dati (`venueId` su ogni tabella) e raggiungibile sul proprio sotto-dominio (`locale1.tuodominio.it`, `locale2.tuodominio.it`, ...). Un **Super Admin** (gestore della piattaforma) crea i locali e l'account amministratore di ciascuno; l'**Admin di locale** gestisce solo il proprio locale, senza vedere gli altri.
- **Multi-modulo**: ogni funzione (presenze, HACCP, inventario, menù, ...) è un modulo indipendente, visibile in base al ruolo dell'utente autenticato.
- **Mobile-first / PWA**: l'app dev'essere pienamente usabile da smartphone (i dipendenti timbrano da telefono inquadrando un QR, i clienti leggono il menù da QR al tavolo), installabile come PWA, e predisposta per un wrapper Android (Capacitor) senza modifiche architetturali.
- **Deploy su piattaforme container esistenti**: nessun reverse proxy "nostro" da gestire — l'app si appoggia al reverse proxy già presente su **Portainer** (tipicamente Nginx Proxy Manager/Traefik) o **Coolify** (Traefik integrato), che si occupano di TLS e instradamento per dominio/sotto-dominio.
- **Material Design coerente**: **MUI (Material UI) v5**, unica libreria UI e unica libreria icone (**Material Symbols/Icons** via `@mui/icons-material`) per l'intera app — niente mix di framework CSS/icone diversi, tema chiaro/scuro definito centralmente, componenti puliti e accessibili.
- **Nessuna eliminazione senza conferma**: qualunque azione distruttiva (elimina timbratura, dipendente, attività, voce di menù, prodotto, ...) deve passare dal componente condiviso `ConfirmDialog` (`frontend/src/components/ConfirmDialog.tsx`) — mai `window.confirm()` del browser, mai una chiamata diretta alla mutation dal click. Vale per ogni nuova funzione di eliminazione, non solo per quelle già presenti.
- **Sicurezza e tracciabilità**: dato che si maneggiano dati di presenza (rilevanti ai fini giuslavoristici) e controlli HACCP (rilevanti in caso di ispezione ASL), ogni inserimento/modifica è tracciato con audit log e timestamp immutabili lato server. L'isolamento fra locali (tenant) è imposto lato server ad ogni query, non solo lato UI.

## 3. Architettura multi-tenant

```
                DNS: *.tuodominio.it  →  IP del server (record wildcard)
                                │
                 ┌──────────────────────────────┐
                 │  Reverse proxy di Portainer/   │   (Traefik/NPM — non nostro,
                 │  Coolify — TLS wildcard         │    già presente sulla piattaforma)
                 └───────────────┬────────────────┘
                                   │  Host: locale1.tuodominio.it, locale2...
                          ┌────────▼─────────┐
                          │ Frontend (Nginx)   │  1 solo container per TUTTI i locali
                          │ React + MUI (PWA)  │  serve la stessa SPA a ogni sotto-dominio
                          │ proxy /api → API   │
                          └────────┬───────────┘
                                    │ stesso host (no CORS)
                          ┌─────────▼──────────┐
                          │   Backend API        │
                          │   NestJS              │
                          │ TenantMiddleware:      │
                          │ Host header → Venue    │
                          └───┬────────────┬──────┘
                              │            │
                  ┌───────────▼──┐   ┌─────▼──────┐
                  │ PostgreSQL    │   │  Redis      │
                  │ (righe con    │   │ (BullMQ)    │
                  │  venueId)     │   └──┬──────────┘
                  └───────────────┘       │
                          ┌────────────────┼─────────────────┐
                   ┌──────▼─────┐  ┌───────▼──────┐  ┌────────▼──────┐
                   │Worker email │  │Worker stampa  │  │Worker report  │
                   └─────────────┘  └───────────────┘  └───────────────┘
```

**Come funziona la risoluzione del tenant:**
1. Il reverse proxy (Portainer/Coolify) instrada **tutti** i sotto-domini `*.tuodominio.it` verso lo stesso container frontend (un solo router/regola, wildcard — non uno stack per locale).
2. Nginx nel container frontend serve la SPA e fa da proxy trasparente di `/api/*` verso il backend, cosicché frontend e API siano sempre sotto lo **stesso sotto-dominio** (niente CORS, niente configurazione per-locale lato client).
3. Un `TenantMiddleware` in NestJS legge l'header `Host` di ogni richiesta:
   - se il sotto-dominio corrisponde a un `Venue.slug` esistente → la richiesta è "nel contesto" di quel locale (usato per il menù pubblico, non autenticato);
   - se il sotto-dominio è quello riservato all'amministrazione (es. `admin.tuodominio.it`) → richiesta "host di piattaforma", riservata al Super Admin;
   - in sviluppo locale (senza sotto-domini) il controllo è disattivato.
4. Per le richieste **autenticate**, l'isolamento vero è dato dal `venueId` contenuto nel JWT (impostato al login) e usato da **ogni query** dei servizi: un Admin di locale non può in nessun caso leggere/scrivere dati di un altro `venueId`, indipendentemente dal sotto-dominio da cui arriva. Il login verifica comunque che l'utente appartenga al locale del sotto-dominio da cui sta accedendo (eccetto il Super Admin, che accede solo dall'host di amministrazione).
5. Le stampanti Epson POS di rete restano raggiungibili in **TCP diretto sulla porta 9100** dal container backend: per questo, se il deploy è su VPS cloud, serve una VPN/agente locale verso la LAN del locale (vedi §9).

## 4. Modelli di dominio (schema dati, riassunto)

Schema completo in `backend/prisma/schema.prisma`. Entità principali:

- **Venue** (locale) — `slug` univoco (sotto-dominio), nome, stato attivo/sospeso. Creato dal Super Admin.
- **User** — account di login: `SUPER_ADMIN` (nessun `venueId`, trasversale), `ADMIN`/`MANAGER`/`EMPLOYEE` (sempre legati a un `Venue`).
- **Role** — enum `SUPER_ADMIN | ADMIN | MANAGER | EMPLOYEE` (RBAC leggero; espandibile a permessi granulari in v2).
- **Employee** — anagrafica dipendente (nome, mansione, reparto, email, telefono, data assunzione).
- **QrToken** — token univoco per postazione fisica di timbratura.
- **AttendanceRecord** — timbrature (inizio/fine turno), `source` (QR/manuale/corretta), `correctedBy`, `note`.
- **LeaveRequest** — richieste assenza (ferie/permesso/malattia), giornata intera o parziale, stato (`PENDING/APPROVED/REJECTED`).
- **Fridge** — frigorifero/congelatore numerato, con range di temperatura accettabile.
- **TemperatureReading** — rilevazione temperatura, `outOfRange` calcolato, `correctiveAction` obbligatoria se fuori soglia.
- **HaccpReport** — istanza di report giornaliero generato/stampato/firmato.
- **Printer** — stampante POS di rete configurata dall'admin di locale (IP, porta, uso: HACCP/ordini).
- **ProductCategory / Product / Supplier / Order / OrderLine** — catalogo, scorte standard e flusso ordini; `Supplier.orderDays` (interi 1–7, lun–dom) indica i giorni ricorrenti in cui va fatto l'ordine, impostati dall'admin e usati per il promemoria in home (vedi §5.6).
- **MenuCategory** — categoria del menù online (es. "Antipasti", "Primi", "Vini"), con ordinamento.
- **MenuItem** — voce di menù: nome, descrizione, prezzo, foto, `allergens` (i 14 allergeni UE, enum), finestra di disponibilità oraria (`LUNCH`/`DINNER`/`ALL_DAY`), `visible` (mostra/nascondi dal menù pubblico), `unavailableUntil` (temporaneamente esaurito fino a una data/ora, calcolato automaticamente come non disponibile finché quel momento non è passato).
- **Task** — attività/scadenza (es. pagamento fornitore, visita medica dipendente, scadenza attestato): `type` (enum), `dueDate`, `status` (`OPEN/DONE`), `recurrence` (`NONE/MONTHLY/YEARLY`, genera automaticamente l'occorrenza successiva al completamento), `reminderDaysBefore` (da quanti giorni prima segnalarla come imminente in home), collegabile a un `Employee` (`relatedEmployeeId`, es. di chi è la visita medica).
- **AuditLog** — traccia di ogni operazione sensibile (chi, cosa, quando, prima/dopo), sempre scoperta per `venueId`.
- **Notification** — notifiche in-app (richieste ferie, temperature fuori soglia, ordini inviati, ...), esposte via API (lista/segna come letta) e riprese nella home amministrazione.
- **Table** *(§5.7, implementata)* — tavolo censito dall'admin: `label` (numero o nome, es. "12" o "Terrazza 2"), `seats` (posti), `active` (per togliere temporaneamente un tavolo, es. in manutenzione, senza perdere lo storico delle prenotazioni già assegnate).
- **Reservation** *(§5.7, implementata)* — richiesta di prenotazione di un cliente: nome, cognome, email, telefono, `partySize`, data/ora, `isEvent`+nota libera (es. "Compleanno"), note su intolleranze/allergie, altre note, `status` (`PENDING/CONFIRMED/REJECTED/CANCELLED`), uno o più tavoli assegnati (manualmente o in automatico, vedi **ReservationTable** sotto), `rejectionReason` (obbligatoria se rifiutata). Isolata per `venueId` come tutte le altre entità.
- **ReservationTable** *(§5.7, implementata)* — relazione molti-a-molti fra `Reservation` e `Table` (chiave composta `reservationId+tableId`, `onDelete: Cascade` su entrambi i lati): una prenotazione può occupare più tavoli insieme (gruppo grande accostato manualmente dall'admin), non un solo `tableId` scalare come nella prima versione.
- Nuovi campi previsti su **Venue** per le impostazioni del modulo prenotazioni: `reservationsEnabled`, `reservationAutoConfirmMaxSeats` (soglia sopra la quale serve sempre conferma manuale), `reservationSlotDurationMinutes` (durata di occupazione di un tavolo di default, per calcolare sovrapposizioni/turni — sovrascrivibile per singola prenotazione, vedi `Reservation.slotDurationMinutes` sotto), `openingHours` (orari di apertura settimanali, `Json`: un giorno chiuso/aperto per ciascuno dei 7 giorni, con fino a due fasce orarie per giorno per gestire una pausa tra un turno e l'altro — es. pranzo e cena; sostituisce i vecchi campi fissi `lunchStart/lunchEnd/dinnerStart/dinnerEnd`, usato sia dal menù per la disponibilità oraria §5.4 sia dalle prenotazioni §5.7).
- **Reservation** ha anche `proposedReservedAt` (nuovo orario proposto dal locale, in attesa di conferma del cliente — non sostituisce `reservedAt` finché il cliente non conferma) e `slotDurationMinutes` (durata di occupazione per questa singola prenotazione: se non impostata, usa il default del locale).

## 5. Moduli funzionali

### 5.0 Gestione locali (Super Admin)

Modulo trasversale, non legato a un `venueId` (è il Super Admin che li amministra):

- **Elenco locali**: nome, sotto-dominio (`slug`), stato (attivo/sospeso), data creazione.
- **Nuovo locale**: il Super Admin inserisce nome e `slug` (validato: solo lettere minuscole/numeri/trattini, univoco) → crea il `Venue` e contestualmente il primo account **Admin di locale** (email + password provvisoria, da cambiare al primo accesso).
- **Sospensione locale**: disattiva l'accesso di tutti gli utenti di quel locale senza cancellare i dati (utile in caso di mancato pagamento/cessata attività).
- Il Super Admin **non** opera sui dati operativi di un locale (presenze, HACCP, ordini, menù): quello resta esclusivo dell'Admin/Manager del locale. Un accesso di supporto da parte del Super Admin ai dati di un locale, se mai servisse, va tracciato esplicitamente (fuori scope v1).

### 5.1 Presenze dipendenti

**Metodi di timbratura verificata — l'admin ne abilita anche più di uno insieme (`Venue.clockIn*Enabled`):**
1. **QR di postazione** (anti-frode, presenza fisica): l'admin genera/stampa un QR per ogni postazione (es. ingresso), che incapsula un URL tipo `https://locale1.tuodominio.it/clock/{qrToken}`. Il dipendente lo inquadra → apre la PWA del **proprio** locale già loggata sulla pagina di timbratura. Registrata con `source: QR`.
2. **GPS**: l'admin imposta una volta la posizione del locale (cattura dal browser) e un raggio in metri (default 20). Dalla home, il dipendente preme il pulsante GPS: il browser chiede la posizione, il server ricalcola la distanza dal punto del locale (formula haversine) e rifiuta se fuori raggio. Le coordinate esatte del locale non sono mai esposte al client, solo i metodi abilitati. Registrata con `source: GPS`.
3. **Tag NFC**: l'admin censisce in app un'etichetta e un testo per ogni tag, poi scrive lo stesso testo sul tag fisico con un'app di terze parti (BarManager non scrive NFC, solo legge). Dalla home, il dipendente avvicina il telefono al tag (Web NFC — Chrome su Android): il testo letto è confrontato con quelli censiti per il locale. Registrata con `source: NFC`.
4. **Diretta dall'app** (fallback): se il locale non ha abilitato nessuno dei tre metodi sopra, resta disponibile il pulsante diretto senza verifica, come in v1. Registrata con `source: MANUAL`.

In tutti i casi: stato corrente evidenziato in home, timestamp sempre server-side (mai quello del client). Anti-doppio-click: se l'ultimo evento è "inizio" senza "fine", il pulsante mostra solo "Fine turno" e viceversa.

**Amministrazione:** vista tabellare (storico timbrature) con correzione manuale (data/ora + motivo obbligatorio, `source: CORRECTION`, tracciata in audit log) e filtri per dipendente e intervallo date. L'**export XLS/PDF** applica sempre gli stessi filtri correnti (dipendente + intervallo date), non l'intero storico del locale: `GET /attendance/export/xlsx` e `/export/pdf` accettano `employeeId` esattamente come l'endpoint di lista (`GET /attendance`) — prima accettavano solo `from`/`to`, quindi filtrare per dipendente in pagina e poi esportare produceva un file con **tutti** i dipendenti, incoerente con quanto mostrato a video. QR di postazione, tag NFC e metodi abilitati si gestiscono dalla sezione "Metodi di timbratura".

**Richieste assenza (dipendente):** form tipo/giorno intero-parziale/note; **approvazione (admin/responsabile):** coda pendenti, approva/rifiuta con nota. Ogni richiesta mostra sia la data in cui è stata inviata sia, una volta decisa, la data di approvazione/rifiuto (`LeaveRequest.createdAt`/`reviewedAt`, già salvate dal backend fin dalla prima versione — mancava solo mostrarle in pagina). L'email del locale (Impostazioni locale, non l'email di login del singolo utente — v. §5.9) riceve un avviso su ogni nuova richiesta, come già per le prenotazioni: solo informativo, l'approvazione resta dall'app. Alla decisione (approvata/rifiutata, con l'eventuale nota), il **dipendente** riceve a sua volta un'email di conferma/rifiuto — all'email di contatto propria (`Employee.email`, usata anche per CC ordini) se impostata, altrimenti all'email di login del suo account collegato (`Employee.user.email`); nessuna delle due presente (dipendente senza account e senza email di contatto) → nessuna email, non un errore.

**Sovrapposizioni e annullamento:** alla creazione di una richiesta, il backend verifica se si sovrappone (anche solo in parte) con un'altra richiesta **attiva** (`PENDING`/`APPROVED`, non `REJECTED`) dello stesso dipendente, e se sì lo segnala — sia come avviso immediato a chi la crea (toast di attenzione, non un blocco: la richiesta viene comunque creata, può capitare in buona fede, es. una correzione), sia nel messaggio della notifica in-app ai responsabili, sia come indicatore persistente ("Si sovrappone con un'altra richiesta") sulle card della richiesta ovunque compaia in lista (le mie richieste, coda del locale, richieste approvate) finché la sovrapposizione resta. Il **dipendente può annullare da sé una propria richiesta** in qualunque momento (non solo se ancora `PENDING`, anche se già `APPROVED` — i piani possono cambiare), cosa che prima poteva fare solo l'admin/responsabile e solo su richieste già approvate di un altro dipendente (quel percorso resta invariato, v. sotto): quando lo fa, l'email del locale ne viene informata, sullo stesso principio della notifica di nuova richiesta. Una richiesta già `REJECTED` non si annulla (è già decisa, non c'è nulla da annullare).

### 5.2 Controlli HACCP

- L'admin censisce i frigoriferi/congelatori (nome/numero, ubicazione, range temperatura accettabile).
- Inserimento giornaliero temperature da form mobile; valore fuori soglia → evidenza rossa + **azione correttiva obbligatoria** + notifica al responsabile.
- Report giornaliero: **stampa su stampante POS Epson di rete** con spazio firma manuale, oppure **firma digitale a video** (pad firma → immagine nel PDF).
- Storico consultabile e riesportabile in qualsiasi momento.

### 5.3 Inventario e ordini

- Categorie e prodotti/formati con `standardQty` (scorta obiettivo), fornitore predefinito.
- **Nuovo ordine**: scelta fornitore → giacenza per prodotto → calcolo automatico `quantità da ordinare = max(0, standardQty − giacenza)`, modificabile.
- Alla conferma: **email** al fornitore (CC automatico ai responsabili di reparto) + **stampa POS** della checklist per il controllo scarico merce. Storico ordini per affinare la `standardQty` nel tempo.
- **Email al fornitore**: intestazione con nome, indirizzo, città e partita IVA del locale (`Venue.city`/`Venue.vatNumber`, impostabili in Impostazioni locale §4 insieme a nome/indirizzo/telefono — prima assenti), oltre al logo se impostato (stesso meccanismo di intestazione delle email di prenotazione, §5.7: l'email ha ora sempre anche un corpo HTML, non solo testo, perché è lì — non nel testo puro — che `MailService.send` inserisce il logo).

### 5.4 Menù online

Gestione del menù del locale, consultabile pubblicamente (es. da QR al tavolo) senza bisogno di login.

**Amministrazione (Admin/Manager):**
- **Categorie** menù create liberamente (es. Antipasti, Primi, Secondi, Dolci, Vini, Birre...), con ordinamento drag&drop.
- Per ogni **voce di menù**: nome, foto (upload, con anteprima e ritaglio), prezzo, descrizione, **allergeni** selezionabili dall'elenco ufficiale dei 14 allergeni UE (reg. 1169/2011: glutine, crostacei, uova, pesce, arachidi, soia, latte, frutta a guscio, sedano, senape, sesamo, solfiti, lupini, molluschi) mostrati come icone/chip.
- **Disponibilità oraria**: ogni voce può essere marcata `Solo pranzo`, `Solo cena` o `Tutto il giorno`; il menù pubblico mostra automaticamente solo le voci pertinenti all'orario corrente (calcolato lato server in base al fuso orario del locale e agli orari di apertura settimanali configurati dall'admin, `Venue.openingHours` — la prima fascia del giorno corrente equivale a "pranzo", la seconda a "cena").
- **Visibilità**: interruttore rapido "mostra/nascondi dal menù" per togliere temporaneamente una voce senza cancellarla.
- **Temporaneamente non disponibile fino a**: selezione data/ora — la voce resta visibile nel menù ma marcata "non disponibile" (es. esaurita) fino al momento indicato, dopo il quale torna automaticamente ordinabile senza bisogno di un'azione manuale.

**Menù pubblico (nessun login):**
- Pagina raggiungibile su `https://locale1.tuodominio.it/menu` (anche da QR al tavolo), risolta automaticamente in base al sotto-dominio.
- Voci raggruppate per categoria, filtrate per orario corrente e visibilità; badge allergeni; badge "non disponibile" per le voci temporaneamente esaurite.
- Nessun dato sensibile esposto: solo le informazioni pubbliche della voce di menù.

### 5.5 Attività e scadenze

Modulo generico per tenere traccia di impegni con una data entro cui vanno fatti, che non rientrano negli altri moduli: pagamento fornitori, visita medica dipendenti, scadenza attestati/corsi obbligatori, manutenzioni.

- Ogni attività ha titolo, descrizione libera, tipo (pagamento fornitore / visita medica / scadenza attestato / manutenzione / generica), scadenza, ed **entro quanti giorni prima** va segnalata come imminente in home (`reminderDaysBefore`, default 7).
- Può essere collegata a un dipendente (es. "Visita medica — Mario Rossi").
- **Ricorrenza**: non ricorrente, mensile o annuale — utile per scadenze periodiche come il rinnovo di un attestato. Al completamento di un'attività ricorrente viene creata subito la prossima occorrenza con la scadenza spostata di un mese/anno, così non va reinserita a mano ogni volta.
- Le attività aperte, evidenziando quelle scadute, alimentano la home dell'amministrazione (§5.6).

### 5.6 Home dell'amministrazione

All'accesso, Admin e Manager vedono in cima alla home un riepilogo di ciò che richiede attenzione **oggi**, prima ancora dei moduli:

- **Richieste dei dipendenti in attesa** (richieste ferie/permessi/malattia non ancora approvate/rifiutate), con approvazione/rifiuto rapido direttamente dalla card, senza dover entrare nel modulo Presenze.
- **Ordini da fare oggi**: fornitori il cui giorno di ordine ricorrente (impostato in "Fornitori", vedi §5.3) coincide con il giorno corrente (es. ogni lunedì, o lunedì e giovedì), con collegamento diretto al flusso "nuovo ordine" per quel fornitore.
- **Scadenze imminenti/scadute** dal modulo Attività e scadenze, con conteggio delle scadute e completamento rapido.
- **Altre notifiche** del giorno (temperature HACCP fuori soglia, ordini inviati, richieste ferie riviste, ...), con possibilità di segnarle come lette.

Se non c'è nulla che richiede attenzione, la sezione lo segnala esplicitamente invece di restare vuota. I moduli operativi restano comunque disponibili come tile sotto il riepilogo, per l'uso normale.

### 5.7 Prenotazioni tavoli *(implementata — v1: assegnazione anche a più tavoli insieme (manuale, non automatica), overbooking configurabile (illimitato o soglia di posti extra, non solo blocco rigido), nessuna cancellazione self-service; vedi §10 per le estensioni ancora aperte)*

Modulo per raccogliere prenotazioni online senza che il cliente debba telefonare: conferma automatica per le richieste piccole quando c'è posto, revisione manuale del locale per quelle grandi o quando la capienza è al limite.

**Pagina/widget pubblico (nessun login):**
- Raggiungibile su `https://locale1.tuodominio.it/prenota`, stessa risoluzione per sotto-dominio del menù pubblico (§5.4); pensata anche per essere **embeddata come widget** (`<iframe>`) nel sito esterno del locale, se ne ha uno.
- Il cliente inserisce: nome, cognome, email, telefono, numero di persone, data e orario, note libere, eventuali intolleranze/allergie ed **evento** opzionale (interruttore "È per un'occasione speciale?" + testo libero, es. "Compleanno").
- Due caselle di consenso, entrambe **preattivate di default**: il consenso marketing (facoltativo, disattivabile liberamente — v. §5.8) e l'**autorizzazione al trattamento dei dati personali** (`Reservation.privacyPolicyConsent`, **obbligatoria**): se disattivata, il pulsante "Prenota" si disabilita e appare un avviso ("Devi autorizzare il trattamento dei dati personali per poter prenotare"); il backend rifiuta comunque la richiesta (`BadRequestException` in `ReservationsService.createPublicReservation`) se qualcuno la manda senza, anche bypassando il frontend. Non richiesta per l'aggiunta manuale dello staff (v. sotto): lì il campo è semplicemente assente dal form ed è forzato a `true` lato backend, dato che non è "il cliente stesso a compilare il form online".
- L'orario proponibile è vincolato agli orari di apertura settimanali del locale (`Venue.openingHours`, §4 — giorno per giorno: chiuso/aperto, con fino a due fasce orarie per gestire una pausa tra un turno e l'altro, es. pranzo e cena), a un orizzonte massimo di prenotabilità (es. 30 giorni, configurabile), a un **anticipo minimo** configurabile (v. sotto) e ai **15 minuti**: il campo orario non è un semplice `<input type="time">` (che permetterebbe comunque di digitare un minuto qualsiasi) ma un selettore a scelta vincolata su un elenco fisso di orari ai quarti d'ora (:00/:15/:30/:45, con ricerca testuale per trovarli rapidamente — stesso componente `QuarterHourTimeField` riusato anche in amministrazione), oltre alla validazione lato server. Gli orari di apertura **non sono mostrati** in pagina (né come elenco settimanale né come didascalia sotto la data scelta): il vincolo resta comunque attivo "in silenzio" — il campo Orario offre solo gli slot ai 15 minuti realmente aperti per il giorno scelto (`quarterHourOptionsForDay` in `PublicReservation.tsx`), e se quel giorno è tutto chiuso il campo resta disabilitato con un avviso generico ("Il locale è chiuso in questo giorno: scegli un'altra data"), senza elencare gli orari di apertura effettivi.
- All'invio il cliente riceve subito un'email: "richiesta ricevuta, in attesa di conferma" oppure, se confermata automaticamente (vedi sotto), "prenotazione confermata" con data/ora/numero di persone.

**Calcolo disponibilità e blocco overbooking:**
- Ogni prenotazione occupa i tavoli per una finestra di tempo pari a `data/ora scelta` + durata (default proposto: 120 minuti, `Venue.reservationSlotDurationMinutes`, impostabile per gestire sia "un turno = tutto il servizio" sia più turni nello stesso servizio, cioè il tavolo si libera e può essere riprenotato più avanti nella stessa fascia) — **oppure**, se impostata, la durata specifica di quella prenotazione (`Reservation.slotDurationMinutes`, modificabile dall'admin per singola prenotazione: es. un tavolo prenotato per una cena più lunga del solito).
- I **posti disponibili** per una data/ora richiesta = somma dei posti di tutti i tavoli attivi − somma dei posti delle prenotazioni (`PENDING` o `CONFIRMED`) la cui finestra si sovrappone a quella richiesta.
- Se la nuova richiesta supererebbe i posti disponibili, viene **bloccata**: il cliente vede un messaggio del tipo "al momento non ci sono posti disponibili per l'orario scelto" (con eventuale proposta di un orario alternativo), e viene generato un **Alert per l'admin** (notifica in-app, riusando il modello `Notification` già esistente, §4) — utile per capire quando la domanda supera la capienza e valutare se aprire altri turni/tavoli.

**Conferma automatica vs manuale:**
- Impostazione admin: **soglia massima di posti per la conferma automatica** (`x`, default proposto 6, in "Impostazioni prenotazioni").
- Richiesta con posti **≤ x** e capienza disponibile: il sistema tenta l'**assegnazione automatica di un singolo tavolo** (algoritmo sotto); se lo trova, la prenotazione passa subito a `CONFIRMED` e il cliente riceve l'email di conferma senza attese. Se non lo trova (nessun tavolo singolo con posti sufficienti, anche se la capienza totale ci sarebbe combinando più tavoli — l'assegnazione automatica **non** combina mai più tavoli, vedi sotto), resta `PENDING` senza tavolo assegnato per revisione manuale.
- Richiesta con posti **> x**: resta **sempre** `PENDING` e richiede conferma manuale dell'admin, **anche se** l'assegnazione automatica ha già trovato un tavolo adatto (in tal caso il tavolo suggerito è già precompilato: l'admin deve solo confermarlo o cambiarlo). I gruppi grandi/gli eventi meritano un controllo umano — disponibilità reale, esigenze particolari, eventuale conferma telefonica.

**Algoritmo di assegnazione automatica (massimizzare l'occupazione):**
- Tra i tavoli attivi e liberi nella finestra richiesta (nessuna prenotazione `PENDING`/`CONFIRMED` sovrapposta su quel tavolo), si sceglie il **più piccolo tavolo con posti sufficienti** (posti ≥ persone richieste, tavoli ordinati per posti crescenti — strategia *best-fit*): lascia liberi i tavoli grandi per i gruppi che ne hanno davvero bisogno, invece di sprecare un tavolo da 8 per una coppia.
- Se nessun tavolo singolo basta, l'assegnazione automatica non interviene: resta all'admin decidere di accostare fisicamente più tavoli e assegnarli tutti insieme a mano (§10 — la modellazione esplicita di più tavoli per la stessa prenotazione, prima solo una possibile estensione v2, è ora implementata: vedi "Amministrazione" sotto).

**Amministrazione:**
- **Tavoli**: CRUD — numero/nome e posti per tavolo, disattivabile senza perdere lo storico delle prenotazioni già assegnate.
- **Prenotazioni**: coda su tre schede — **Da confermare** (`PENDING`), **Confermate** (`CONFIRMED`, con le prenotazioni ancora senza tavolo assegnato **raggruppate in cima** sotto l'etichetta "Da assegnare a un tavolo", invece di una scheda a parte come nella prima versione — sia richieste online rimaste manuali sia aggiunte a mano senza sceglierne uno), **Rifiutate e annullate** (`REJECTED`+`CANCELLED` **uniti nella stessa scheda, senza divisioni**: lo stato resta visibile sul chip di ogni card, ma non ci sono due tab separati da controllare). Il backend accetta un elenco di stati separato da virgole nel filtro (`GET /reservations?status=REJECTED,CANCELLED`) apposta per questo raggruppamento. Azioni rapide **Accetta**/**Rifiuta** (il rifiuto richiede un motivo, riportato al cliente via email); **riassegnazione manuale dei tavoli** in qualsiasi momento, anche su una prenotazione già confermata — il campo è un **Autocomplete a selezione multipla con ricerca testuale** (digitando si filtra l'elenco per numero/nome del tavolo), non un semplice menu a tendina: permette di assegnare **più di un tavolo insieme** alla stessa prenotazione, per i gruppi troppo grandi per un tavolo singolo (es. un tavolo da 4 + uno da 6 per 10 persone). Il menu di scelta **esclude del tutto** i tavoli occupati da un'altra prenotazione attiva nello stesso orario: non compaiono come opzione, e assegnarli è comunque rifiutato lato server anche a costo zero di UI bypassata (a differenza della capienza totale/overbooking, qui non c'è override di backoffice — un tavolo non può mai essere condiviso da due prenotazioni nello stesso momento, indipendentemente da quanti altri tavoli quelle prenotazioni occupano). Contatore "posti disponibili" per data/servizio sempre visibile.
- **Cambia orario**: l'admin può proporre un nuovo orario per una prenotazione già presa in carico (all'accettazione o in un secondo momento). Non cambia subito l'orario: il cliente riceve un'email con un link "Confermo il nuovo orario" e solo quando lo clicca la prenotazione viene aggiornata (stesso principio anti-phishing dei pulsanti Accetta/Rifiuta — nessuna azione al solo apertura del link). Finché la conferma non arriva, la coda mostra un chip "in attesa di conferma nuovo orario" sulla card.
- **Modifica prenotazione**: a differenza del cambio orario, permette di correggere dati cliente, note e la durata di occupazione di quella singola prenotazione senza richiedere conferma del cliente — pensata per correggere un errore di inserimento o aggiornare una nota, non per rinegoziare l'appuntamento.
- **Aggiunta manuale** (telefono, di persona, ecc.): lo staff può sempre registrare una prenotazione dal backoffice, con gli stessi campi del widget pubblico (più una durata di occupazione opzionale, se diversa dal default del locale, e più tavoli scelti insieme se serve). A differenza del widget pubblico, l'aggiunta manuale **non applica** il calcolo di disponibilità/capienza totale né il blocco overbooking, e i tavoli sono opzionali (se non scelti, la prenotazione compare comunque tra le Confermate, raggruppata in cima come "da assegnare a un tavolo"); nasce direttamente `CONFIRMED` (considerata già accettata da chi la inserisce), non `PENDING`. Lo stesso Autocomplete multiplo con ricerca testuale della coda, qui applicato prima ancora che la prenotazione esista, esclude in tempo reale i tavoli occupati per la data/ora/durata scelte — non è possibile assegnarne uno già occupato nemmeno dall'aggiunta manuale. Un campo di ricerca separato permette di "pescare" i dati di un cliente già prenotato in precedenza (per nome, email o telefono) invece di reinserirli da zero.
- **Cliente che riprenota**: se l'email di una prenotazione coincide con quella di richieste precedenti allo stesso locale, la coda mostra un pulsante "storico cliente" che apre l'elenco delle sue prenotazioni passate (stesso pulsante anche nel dialog di aggiunta manuale, non appena si seleziona/digita un cliente esistente). Oltre a questo, ogni prenotazione crea/aggiorna automaticamente una riga nell'anagrafica clienti dedicata — vedi §5.8.
- **Overbooking configurabile**: in Impostazioni prenotazioni l'admin può impostare l'overbooking del widget pubblico come **illimitato** (il blocco per capienza superata non scatta mai) oppure con una **soglia di posti extra** tollerati sopra la capienza totale dei tavoli attivi prima di bloccare (0 = blocco rigido, comportamento di base). Questa tolleranza riguarda solo le richieste dal widget pubblico: l'aggiunta manuale in backoffice non ha mai questo vincolo.
- **Impostazioni prenotazioni**: attiva/disattiva il modulo, soglia posti per conferma automatica, durata di occupazione del tavolo di default (minuti), orizzonte massimo di prenotabilità, overbooking (illimitato o soglia di posti extra), **anticipo minimo** (`Venue.reservationMinLeadMinutes`, ore+minuti in UI ma un unico intero di minuti in DB — es. 30 impedisce di prenotare dal widget pubblico per un orario a meno di 30 minuti da adesso; 0 = nessun vincolo, comportamento storico). L'anticipo minimo, come l'overbooking, **non si applica** all'aggiunta manuale in backoffice, ed è validato solo alla creazione (`ReservationsService.createPublicReservation`), non nel semplice calcolo di disponibilità (`getAvailability`, usato anche dall'amministrazione), altrimenti quel contatore smetterebbe di funzionare per un orario ormai troppo vicino anche quando nessuno sta creando nulla. Gli **orari di apertura** (giorni/fasce, usati sia per validare l'orario prenotabile sia dal menù online) si impostano separatamente in Impostazioni locale (§4).
- Una volta implementato, le prenotazioni in attesa di conferma e i blocchi per overbooking alimenterebbero anche la home dell'amministrazione (§5.6), sullo stesso principio delle richieste ferie e degli ordini del giorno.
- **Notifica email al locale**: ad ogni nuova prenotazione, l'indirizzo email del locale (Impostazioni locale) riceve un'email con i dati della richiesta e, se serve conferma manuale, due pulsanti **Accetta**/**Rifiuta**. I pulsanti aprono una pagina pubblica di gestione (nessun login, identificata da un token opaco della prenotazione — non eseguono l'azione al solo apertura del link, per non farla scattare da sola se un antivirus/filtro anti-phishing "visita" i link in automatico) dove si può anche scegliere/cambiare il tavolo prima di confermare. Se il locale non ha impostato una propria email, questa notifica è semplicemente saltata (resta comunque l'Alert in-app per gli admin già loggati).
- **Email al cliente su ogni cambio di stato**: chi prenota riceve sempre un'email — "richiesta ricevuta, in attesa di conferma" se resta `PENDING`, oppure "prenotazione confermata" se viene confermata (subito in automatico, o dopo l'accettazione del locale/dal link email), "prenotazione non confermata" con il motivo se viene rifiutata, e "prenotazione annullata" se il locale la annulla (es. il cliente disdice per telefono). Nessuna di queste email richiede un account: usano sempre l'indirizzo email inserito al momento della prenotazione.
- **Auto-gestione del cliente entro 15 minuti dalla richiesta**: le email "richiesta ricevuta" e "prenotazione confermata" includono un link a una pagina pubblica dedicata (`/prenota/modifica/:id`, senza login, diversa da quella dello staff) dove il cliente può correggere da sé nome/cognome/telefono/numero di persone/occasione speciale/note, oppure annullare direttamente — ma solo entro **15 minuti dalla creazione della richiesta** (non dall'orario prenotato): oltre quel termine la pagina mostra l'invito a contattare il locale (al numero di telefono impostato in Impostazioni locale, `menuPhone`, se presente) per qualsiasi modifica. Non copre l'orario della prenotazione (resta un'azione del locale, proponi/conferma sopra) né i tavoli (di competenza dello staff). **Ogni modifica del cliente riporta la prenotazione a `PENDING`**, qualunque fosse lo stato prima (anche se già `CONFIRMED`): il locale deve sempre rivedere/riconfermare, riusando lo stesso meccanismo di una richiesta nuova (email al locale con Accetta/Rifiuta, `Notification` in-app). L'**annullamento** invece non richiede conferma del locale (solo un avviso in-app, `RESERVATION_CANCELLED_BY_CUSTOMER`): annullare non ha bisogno di revisione. Endpoint pubblici dedicati (`GET/PATCH /public/reservations/:id/self`, `PATCH /public/reservations/:id/self/cancel`), separati da quelli dello staff (`:id/manage/...`) apposta per non esporre mai Accetta/Rifiuta al cliente.
- **Logo nell'intestazione email**: se impostato un logo in Impostazioni locale (`Venue.logoUrl`, distinto dalla copertina del menù pubblico), viene anteposto come immagine in alto in tutte le email HTML di questo modulo (cliente e locale) — gestito centralmente da `MailService.send` (`common/mail/mail.service.ts`, §7), non da ciascun template; l'URL assoluto è costruito da `venueLogoAbsoluteUrl` (`common/venue-url/venue-url.ts`), condiviso anche dal modulo Ordini (§5.3), che lo usa allo stesso modo. Il file caricato viene sempre **convertito in PNG** con `sharp` all'upload (`POST /venues/me/logo`), a prescindere dal formato originale (jpeg/png/webp): il webp, comodo per la trasparenza sul web, non è supportato in modo affidabile dai client email — la trasparenza risultava mostrata con uno sfondo nero al posto del trasparente; il PNG gestisce comunque la trasparenza e non ha questo problema. Ridimensionato in altezza (240px, senza allargare immagini più piccole) perché in email è mostrato al massimo a 80px. I loghi caricati prima di questa modifica restano nel loro formato originale (quindi ancora potenzialmente problematici in email) finché non vengono ri-caricati.
- **Link "gestisci i tuoi dati personali"**: in fondo a ogni email al cliente (ricevuta, confermata, non confermata, annullata, nuovo orario proposto, modifica in attesa di conferma — non alle email allo staff) c'è un link a una pagina pubblica dedicata (§5.8), sullo stesso principio di un link di cancellazione da una mailing list: il cliente può togliere il consenso marketing o eliminare la propria scheda cliente in autonomia, senza aspettare il locale.

**Integrazione con Google (ricerca/Maps):** tre livelli possibili, con impegno molto diverso — dal semplice link a un vero progetto a parte:

1. **Link di prenotazione su Google Business Profile** *(subito, zero sviluppo lato BarManager)* — ogni locale, dal proprio account Google Business Profile ("Prenotazioni" → "Aggiungi link"), può incollare l'URL della pagina pubblica `/prenota`. Compare come link generico ("Prenota") nella scheda del locale su Search/Maps, di norma attivo entro 24-48 ore. È una configurazione che fa il gestore del locale sul proprio account Google, non richiede nessuna integrazione né codice da parte nostra. Non dà il bottone blu nativo "Prenota" né la disponibilità in tempo reale — solo un link verso il nostro widget.
2. **Dati strutturati sulla pagina pubblica** (`ReserveAction`/`FoodEstablishmentReservation`, schema.org — sviluppo minimo: un blocco JSON-LD con nome locale, orari e l'azione di prenotazione con URL, sulla pagina `/prenota`) — può far comparire un'azione "Prenota" nei risultati di ricerca, ma **non è garantito**: è Google a decidere autonomamente se e quando mostrarlo, non è un'integrazione formale né richiede approvazione.
3. **"Reserve with Google" vero e proprio** (bottone blu nativo + disponibilità in tempo reale su Search/Maps) — richiede che **BarManager stesso** (non il singolo locale) diventi **partner approvato** di Google tramite l'Actions Center (API "Reservations end-to-end"): relazione contrattuale diretta con i locali, indirizzo di ciascuno corrispondente alla sua scheda Google Maps, ed esposizione a Google — in tempo reale — di disponibilità e stato prenotazione nel formato standard richiesto (persone, fasce orarie, conferma), che ricalca bene il modello `Table`/`Reservation` già progettato sopra. È un impegno molto più grande della sola app: domanda di partnership, revisione tecnica di Google, requisiti di affidabilità/performance continui (Google monitora ad es. il tempo medio di completamento di una prenotazione). Va trattato come **progetto separato**, da confermare esplicitamente (§10), non come parte del rilascio v1. Alternativa più rapida ma meno indipendente: integrarsi non direttamente con Google ma con un aggregatore già partner (es. Eat App, Tableo, resOS, SevenRooms) che fa da tramite — a costo di una dipendenza (spesso un abbonamento) da quella piattaforma terza, che finirebbe in parte a sovrapporsi con quanto BarManager offrirebbe già in proprio.

### 5.8 Modulo Clienti *(implementata — v1: CRUD manuale + creazione/aggiornamento automatico da ogni prenotazione + consenso marketing esplicito + import/export xlsx; l'invio di campagne resta fuori scope, vedi sotto)*

Anagrafica clienti dedicata (modello `Customer`, isolato per `venueId` come tutto il resto, unico per email nello stesso locale), pensata per andare oltre il semplice derivare i clienti dalle prenotazioni (come faceva `searchCustomers`/`getCustomerHistory` in §5.7, ancora usate per "pescare" un cliente in fase di aggiunta manuale) e permettere in futuro azioni di marketing (campagne email/SMS/WhatsApp).

- **Creazione/aggiornamento automatico**: ogni nuova prenotazione (dal widget pubblico o aggiunta a mano in backoffice) crea o aggiorna la riga del cliente corrispondente (per email, case-insensitive) — `ReservationsService.createPublicReservation`/`createManualReservation` chiamano `CustomersService.recordReservation` dopo aver salvato la prenotazione. Nome/cognome/telefono vengono aggiornati con i dati dell'ultima prenotazione.
- **`firstReservationAt`** ("registrazione"): impostato solo alla prima prenotazione mai fatta da quell'email per quel locale, non più modificato dopo.
- **`lastReservationAt`**: aggiornato a ogni nuova prenotazione (al momento in cui viene effettuata la richiesta, non alla data/ora futura della prenotazione stessa) — pensato anche come riferimento per un futuro invio di campagne, cioè un proxy di "quanto è recente il rapporto col cliente".
- **`reservationsCount`**: contatore che si incrementa a ogni prenotazione della stessa email.
- **Consenso marketing esplicito (`marketingConsent`)**: raccolto con una casella dedicata ("Accetto di ricevere comunicazioni promozionali...", facoltativa e **preattivata di default** — v. nota su `privacyPolicyConsent` in §5.7) nel widget pubblico di prenotazione (`Reservation.marketingConsent`), propagato al `Customer` corrispondente a ogni prenotazione (l'ultimo valore dichiarato vince, quindi un cliente può anche revocarlo prenotando di nuovo con la casella deselezionata, o dalla pagina "gestisci i tuoi dati personali", v. sotto). **Di sola lettura per l'admin** (pagina "Clienti" e CRUD API): solo il cliente stesso può darlo o ritirarlo, alla prenotazione o da quella pagina — mai lo staff, nemmeno inserendo un cliente a mano (`CreateCustomerDto`/`UpdateCustomerDto` non hanno più questo campo, forzato lì a `false` alla creazione e mai toccato in modifica). Resta invece modificabile in blocco tramite import xlsx (v. sotto), pensato per migrazioni da un altro sistema con consensi già raccolti altrove, non per un cambio dalla singola scheda. A differenza di `lastReservationAt`, questo campo **è** un consenso esplicito ai fini GDPR/e-privacy, perché richiede un'azione volontaria del cliente (non è mai implicito nell'aver semplicemente prenotato).
- **CRUD manuale** (`/customers`, pagina "Clienti"): l'admin può aggiungere, modificare ed eliminare clienti indipendentemente dalle prenotazioni (es. per censire un cliente abituale prima ancora che prenoti online). Le date di prima/ultima prenotazione e il contatore sono di sola lettura quando derivano dal flusso automatico, ma sovrascrivibili tramite import xlsx (v. sotto). La pagina ha anche una barra di ricerca (nome/cognome/email/telefono) e una paginazione (10/25/50/100 righe), entrambe lato client sulla lista già scaricata da `/customers` in un'unica chiamata — nessun nuovo parametro lato backend.
- **Import/export xlsx** (`GET /customers/export/xlsx`, `POST /customers/import/xlsx`, pulsanti "Esporta"/"Importa" in pagina): stesso formato in entrambe le direzioni, colonne identificate per intestazione (non per posizione) — `Client ID, First name, Last name, Email, Phone, Marketing Consent (YES/NO), Total Reservation, Last Reservation Date (YYYY-MM-DD), Last Reservation` (colonna ora separata dalla data). All'import, per ogni riga: `Client ID` assente → nuovo cliente con id generato automaticamente (o, se assente ma l'email combacia con un cliente già esistente, quello viene aggiornato invece di creare un duplicato); `Client ID` presente e trovato in questo locale → dati confrontati e aggiornati; `Client ID` presente ma non trovato → creato un nuovo cliente con quell'id esplicito (utile per migrare id da un altro sistema). Una riga non valida (es. email mancante) non blocca le altre: l'errore è raccolto e mostrato a fine importazione senza interrompere il resto del file. Lettura/scrittura xlsx generiche condivise con gli altri export dell'app (`XlsxService.readSheet`/`buildSheet`, §11).
- **Modulo opzionale** (`ModuleKey 'customers'`, come `reservations`): non incluso nei permessi di default di Manager/Dipendente, l'admin lo concede esplicitamente a chi deve gestirlo (`Employee.allowedModules`, §7).
- **Pagina pubblica "gestisci i tuoi dati personali"** (`/privacy?token=...`, nessun login, link in fondo a ogni email di prenotazione al cliente — §5.7): identificata da `Customer.privacyToken`, un token opaco **unico a livello globale** (non solo per locale, a differenza di `[venueId, email]`) perché è l'unico dato nel link. Generato alla prima prenotazione (`CustomersService.recordReservation`) e mai più cambiato (un link mandato in un'email precedente deve continuare a funzionare); per un cliente creato prima di questo campo, o toccato da un'azione che non passa da `recordReservation` (accetta/rifiuta/annulla/proponi orario), viene generato al bisogno da `CustomersService.ensurePrivacyToken`. Tre azioni, sullo stesso principio di un link di cancellazione da una mailing list: **attivare** (`PATCH /public/customers/privacy/opt-in`) o **togliere** (`PATCH /public/customers/privacy/opt-out`) il consenso marketing — gli unici due punti, insieme alla prenotazione stessa, da cui il cliente può cambiarlo, mai lo staff (v. sopra) — o **eliminare la propria scheda cliente** (`DELETE /public/customers/privacy`), che elimina solo l'anagrafica (`Customer`: nome/cognome/email/telefono/note/consenso). Le prenotazioni già effettuate restano nello storico operativo del locale (§5.7): una scelta tecnica interna, per non corrompere i dati operativi del locale, che non viene esposta al cliente nel testo della pagina (non è un dettaglio che lo riguarda). Endpoint pubblici in `public-customers.controller.ts`, distinti da quelli admin (`customers.controller.ts`, che richiedono login).
- **Non implementato** (fuori scope di questa v1, vedi §10): l'invio vero e proprio di campagne pubblicitarie via email/SMS/WhatsApp — `marketingConsent` identifica chi può essere contattato, ma il canale di invio stesso (provider email/SMS/WhatsApp, template, pianificazione) resta da costruire. Resta inoltre fuori scope un'eventuale cancellazione/anonimizzazione estesa anche alle prenotazioni già effettuate (diritto all'oblio "pieno"): l'eliminazione qui riguarda solo la scheda cliente/marketing, non lo storico prenotazioni, per non corrompere i dati operativi del locale — da valutare separatamente se richiesto.
- **Deduplica automatica per email**: `@@unique([venueId, email])` a livello di database è case-sensitive, mentre ogni percorso di scrittura applicativo (creazione manuale, import, upsert da prenotazione) normalizza l'email in minuscolo — quindi righe duplicate per sola differenza di maiuscole/minuscole potevano restare da prima di questa normalizzazione. `CustomerDedupeService` (`OnModuleInit`, gira una volta a ogni avvio del backend, idempotente — non trova più nulla da unire dopo la prima volta utile) raggruppa i clienti dello stesso locale per email normalizzata: se un gruppo ha più di una riga, tiene la più vecchia (`createdAt` più basso) come cliente definitivo, somma `reservationsCount` di tutte le righe del gruppo, e tiene la data di `lastReservationAt` più recente tra tutte (idem per `firstReservationAt`, la più vecchia). Le righe in eccesso vengono eliminate in una singola transazione **prima** di aggiornare quella definitiva (mai il contrario: se la definitiva venisse aggiornata per prima con un `privacyToken` ancora posseduto da una riga non ancora eliminata, violerebbe per un istante il vincolo di unicità globale su quel campo, §5.8).

### 5.9 Profilo utente (autogestione)

Ogni utente autenticato, qualunque ruolo (Admin, Manager, Dipendente, Super Admin), può cambiare i propri dati e la propria password da una pagina dedicata (`/account`, "Il mio profilo"), raggiungibile dalla nuova icona utente in alto a destra nella barra dell'app (prima, solo su desktop, c'era l'email in chiaro con un'icona di logout separata — ora un unico menu con email, "Il mio profilo" ed "Esci", visibile anche da mobile).

- **`GET/PATCH /me`**: email di login (chiunque), più nome/cognome/telefono — questi ultimi solo per chi ha una scheda `Employee` collegata (Manager/Dipendente); per un Admin puro (nessun `Employee`, v. §7) il backend li ignora silenziosamente se inviati, e la pagina non li mostra nemmeno. Un cambio email verificato contro eventuali conflitti con un altro account (`ConflictException` se già in uso).
- **`PATCH /me/password`**: richiede la password attuale (verificata con `argon2.verify`), rifiuta se la nuova coincide con quella attuale.
- **Non è la stessa email delle notifiche del locale**: `User.email` (qui) è l'email di *login* del singolo account; `Venue.email` (Impostazioni locale, §5.7) è l'indirizzo a cui arrivano le notifiche di nuove prenotazioni/richieste ferie — due campi distinti, cambiare l'uno non cambia l'altro.

### 5.10 Ordini online: asporto e consegna a domicilio *(SOLO specifica — non ancora implementata; tutte le decisioni sono state confermate dall'utente, v. §10 — pronta per l'implementazione)*

Estende il menù pubblico (§5.4, oggi solo "consulta") con un vero carrello/checkout: il cliente compone un ordine da asporto (**ritiro in negozio**) o da **consegna a domicilio**, e lo staff lo riceve, prepara e chiude — con integrazione opzionale verso Loyverse come registro vendite (non come orchestratore dell'ordine, per i limiti API descritti sotto). Riusa deliberatamente pattern già esistenti in BarManager invece di inventarne di nuovi: il widget pubblico senza login delle Prenotazioni (§5.7), l'upsert automatico su `Customer` (§5.8), la mappa Leaflet e il calcolo di distanza già usati per la timbratura GPS (§5.1), e la stampa via PDF+browser già usata per gli ordini fornitori (§5.3).

**Due modalità dello stesso catalogo, non due menù separati**: `MenuCategory`/`MenuItem`/`MenuItemVariant` restano un'unica fonte di verità (anche quando sincronizzati da Loyverse, §5.4). Il "menù locale" (QR al tavolo, oggi implementato) resta un semplice catalogo consultabile — **nessuna delle informazioni di consegna/ritiro gli serve**, come richiesto esplicitamente. Il nuovo canale "ordini online" aggiunge solo un interruttore per-voce, non un secondo catalogo:
- `MenuItem.orderableOnline` (bool, default `false`): l'admin abilita esplicitamente solo le voci che vuole vendibili online (es. un cocktail preparato al momento potrebbe restare solo "menù locale"). Stesso trattamento di `visible`/`featured`/`unavailableUntil`: è un flag di **presentazione/canale**, quindi sempre modificabile anche con l'integrazione Loyverse attiva (esente da `assertNotLoyverseManaged`, come le altre voci puramente di visibilità).
- Stesso prezzo/foto/allergeni/descrizione in entrambi i canali in questa v1 — nessun prezzo differenziato per l'online (da confermare in §10 se serve davvero, es. un piccolo sovrapprezzo consegna già incluso nel prezzo voce invece che come costo di consegna separato).

**Due pagine pubbliche distinte, non una sola con un bivio iniziale** — confermato con l'utente, stesso principio già in uso per `/menu` e `/prenota` (due link/QR separati, scelti dal locale, senza schermata "cosa vuoi fare" in mezzo — es. il QR al tavolo continua a puntare solo a `/menu`, un link "Ordina online" separato sul sito/social punta a `/ordina`). Le due pagine restano **esteticamente coerenti fra loro** (stessa copertina, stesso colore di accento, stesse categorie/foto dei prodotti — la stessa "famiglia" visiva) anche se non identiche (`/ordina` ha in più carrello, quantità, checkout). Per chi arriva su `/menu` senza sapere che esiste anche l'ordinazione online, **nuovo link in fondo alla pagina** (footer di `PublicMenu.tsx`, visibile solo se `Venue.onlineOrdersEnabled`): *"Vuoi fare un ordine online? Clicca qui"* → `/ordina` — l'unico punto di collegamento fra le due pagine, che non introduce alcun campo/flusso di consegna dentro `/menu` stessa.

**Modificatori (nuovi, nativi — non solo da Loyverse)**: la richiesta dell'utente sui modificatori Loyverse (letti/creati via API, v. sopra in questa conversazione) riguarda in realtà un concetto che **BarManager non ha ancora in proprio**: oggi solo le Varianti (`MenuItemVariant`, es. Piccola/Grande, con prezzo e nome proprio) esistono nativamente, funzionanti anche senza Loyverse (§88). I Modificatori sono un asse diverso e ortogonale alle varianti (es. "Estras": +Formaggio, -Cipolla, applicabili a più voci diverse), quindi vanno modellati come entità nuove, non come varianti mascherate:
- `MenuModifierGroup` (venue-scoped): nome (es. "Estras"), tipo selezione (`SINGLE` | `MULTIPLE`, come i tre tipi di Loyverse — `QUANTITY_BASED` rimandato a una fase successiva se richiesto), `minSelections`/`maxSelections`.
- `MenuModifierOption`: appartiene a un gruppo, nome (es. "Formaggio extra"), prezzo (può essere 0, es. "Senza cipolla"), `sortOrder`.
- `MenuItemModifierGroup` (molti-a-molti): quali gruppi si applicano a quale voce — un gruppo "Estras" può essere condiviso da più voci diverse, esattamente come in Loyverse (`Item.modifier_ids`).
- Se il locale ha Loyverse attivo, questi gruppi/opzioni si popolano dal sync (lettura, `GET /modifiers` + `Item.modifier_ids`) invece che a mano — stessa logica già applicata a categorie/voci/varianti (fonte unica, editabile solo da Loyverse quando attivo).

**Checkout pubblico (nessun login)**, nuova pagina `/ordina` (a fianco di `/menu` e `/prenota`, stesso schema di risoluzione per sotto-dominio):
1. Carrello con le sole voci `orderableOnline`, scelta varianti/modificatori per riga (stesso `line_note` libero già pensato per Loyverse, utile comunque anche senza Loyverse per "senza ghiaccio" ecc.).
2. Scelta **ritiro** oppure **consegna** (`OnlineOrderFulfillment`): decide quali campi successivi servono, e solo se il canale è aperto in quel momento (v. "Orari e costi di consegna" sotto).
   - **Ritiro**: solo nome/telefono/email (per lo scontrino e per l'anagrafica cliente) — nessun indirizzo, nessuna mappa.
   - **Consegna**: il cliente digita l'indirizzo in chiaro → un pulsante "Cerca" lo **geocodifica** (indirizzo testuale → coordinate) e sposta il puntatore sulla mappa (riuso letterale di `LocationPicker.tsx`, §5.1) sul punto trovato; il cliente può poi correggerlo a mano (clic/drag del marker, o "usa la mia posizione attuale" via `navigator.geolocation`) — la ricerca testuale è solo un punto di partenza comodo, **il punto sulla mappa resta sempre l'origine di verità** per la distanza e per chi consegna, non l'indirizzo testuale (utile per condomini/civici ambigui che il geocoder può sbagliare). **Risolto**: provider **LocationIQ** (API compatibile Nominatim/OSM, piano gratuito con uso commerciale esplicitamente permesso nei termini di servizio — 5.000 richieste/giorno, 2/secondo, unico obbligo un link di attribuzione in pagina — a differenza del solo servizio pubblico Nominatim, non pensato per un uso in produzione). Geocodifica **inversa** (coordinate→indirizzo leggibile, stesso provider) quando il cliente sposta il marker a mano, per confermargli in chiaro cosa ha selezionato. Chiave API **a livello di piattaforma** (variabile d'ambiente, es. `LOCATIONIQ_API_KEY`), non per singolo locale come invece Loyverse/SumUp: LocationIQ non è un account del locale ma un servizio di utilità che BarManager stesso consuma per conto di qualsiasi locale. Distanza dal locale calcolata lato server con la stessa formula haversine già scritta per la timbratura GPS (`distanceMeters` in `attendance.service.ts`, da spostare in un util condiviso `common/geo/geo.ts` visto che ora serve a due moduli): rifiutata se oltre `Venue.deliveryRadiusMeters` (null = nessun limite), sullo stesso schema "illimitato o soglia" già usato per l'overbooking prenotazioni (§5.7).
3. **Orario desiderato di ritiro/consegna** (`OnlineOrder.requestedAt`) — nuova precisazione dell'utente: stessa identica logica già scritta per le Prenotazioni (§5.7, `validateRequestedTime`), non una regola nuova. Il cliente sceglie un orario ai **15 minuti** (es. 20:00/20:15/20:30, non un minuto libero), che deve cadere in una fascia di apertura per quel giorno (`Venue.onlineOrdersOpeningHours`, v. sotto — stesso `resolveOpeningHours`/`findOpenSlot` già condiviso da menù/prenotazioni/ordini), non nel passato, e con lo stesso vincolo di anticipo minimo configurabile (`Venue.onlineOrdersMinLeadMinutes`, equivalente a `reservationMinLeadMinutes` ma un valore proprio: il tempo di preparazione di una pizza non è il tempo di preparazione di un tavolo). **Margine fisso di mezz'ora ad apertura e chiusura di ciascuna fascia cucina** (nuova precisazione dell'utente, valore fisso non configurabile — a differenza di `onlineOrdersMinLeadMinutes` che è "quanto in anticipo da adesso", questo è "quanto dopo l'apertura/prima della chiusura del turno cucina"): per ciascuna fascia (`slot1`/`slot2`) di `onlineOrdersOpeningHours`, il primo orario prenotabile è l'inizio fascia **+30 minuti** e l'ultimo è la fine fascia **-30 minuti** — es. cucina 12:00–15:00 → primo ritiro/consegna prenotabile 12:30, ultimo 14:30. Stesso `findOpenSlot` di base, ma con i limiti della fascia ristretti di 30 minuti su ciascun lato prima del confronto, applicato solo qui (non alle Prenotazioni, dove il tavolo non richiede un "tempo di preparazione" analogo). Come per le prenotazioni (§209), il widget **non mostra un calendario di disponibilità**: è un vincolo silenzioso, verificato lato server alla conferma — il cliente digita/seleziona un orario e riceve un errore leggibile solo se non valido, senza dover consultare prima una tabella di slot liberi/occupati.
4. Dati cliente → **upsert su `Customer`** esattamente come già fa `recordReservation` per le prenotazioni (§5.8): stesso locale, stessa email → stesso cliente, con nuovi contatori paralleli `firstOrderAt`/`lastOrderAt`/`ordersCount` (accanto ai già esistenti `firstReservationAt`/`lastReservationAt`/`reservationsCount`) più `totalOrdersSpent` (somma di `OnlineOrder.total` per gli ordini `COMPLETED` di quel cliente, aggiornata in incremento ad ogni chiusura ordine — non una `SUM` calcolata al volo ad ogni apertura della pagina Clienti, sullo stesso principio dei contatori già esistenti). **Risolto**: `CustomersAdmin.tsx` mostra entrambi i nuovi contatori come colonne proprie — "Ordini online" (numero, `ordersCount`) e "Spesa totale" (`totalOrdersSpent`, formattata in euro) — accanto alla colonna "Prenotazioni" già esistente, non un unico contatore "attività" che li fonderebbe perdendo il dettaglio economico. Stesso consenso privacy obbligatorio (`privacyPolicyConsent`) e stessa casella di consenso marketing opzionale già presenti nel widget prenotazioni.
5. **Pagamento — solo per la consegna**: scelta contanti o carta online (dettaglio integrazione SumUp sotto) prima di confermare l'ordine. **Per il ritiro in negozio questo passaggio non esiste**: il cliente conferma l'ordine senza indicare né pagare nulla — decide e registra il pagamento l'operatore al momento del ritiro fisico, v. sotto.
6. Conferma con **token opaco** (`manageToken`, stesso pattern di `Reservation.manageToken`) per una pagina pubblica di **tracciamento ordine** senza login (stato in tempo reale: ricevuto → confermato → pronto/in consegna → completato), sullo stesso schema della pagina self-service prenotazioni (§5.7).

**Dati precompilati al prossimo ordine (cache lato browser, non lato server)**: nessun login su `/ordina`, quindi niente sessione server su cui appoggiarsi — la soluzione è una cache **locale al dispositivo/browser del cliente** (nuovo store `frontend/src/store/checkoutContactStore.ts`, zustand `persist` in `localStorage` come già `authStore`, chiave dedicata es. `barmanager-order-contact`), naturalmente isolata per locale perché ogni locale vive già sul proprio sotto-dominio (origine diversa = `localStorage` diverso, nessuna logica di scoping aggiuntiva serve). Al primo caricamento della pagina, se c'è una cache salvata, il form si presenta già compilato (nome/cognome/email/telefono, e — se l'ultimo ordine era una consegna — indirizzo testuale + le stesse coordinate scelte sull'ultima mappa), sempre modificabile prima di confermare, mai inviato automaticamente. Aggiornata alla conferma di un ordine riuscito (non ad ogni tasto premuto, per non salvare dati di un carrello abbandonato a metà). Un piccolo link "Non ricordare i miei dati su questo dispositivo" pulisce la cache.
- **Cosa NON viene mai messo in questa cache**: il carrello (si riparte sempre da un carrello vuoto), le caselle di consenso (`privacyPolicyConsent`/`marketingConsent`, sempre riproposte non selezionate — un consenso non va mai riusato silenziosamente da una sessione precedente) e ovviamente nessun dato di pagamento (che comunque BarManager non arriva mai a vedere, v. SumUp sotto).
- Questa cache è **distinta e indipendente** dall'upsert su `Customer` lato server (§5.8): quella è il record aziendale del locale (usato per statistiche/marketing), questa è solo una comodità per l'utente sul proprio dispositivo — un utente che cancella la cache del browser non perde né riduce in alcun modo la propria scheda cliente, e viceversa un admin che modifica/elimina la scheda `Customer` non tocca la cache del dispositivo del cliente.

**Pagamento — due flussi diversi, uno per modalità**:

**Consegna: pagamento al checkout, con SumUp Online Payments API** — **risolto**: si usa esclusivamente l'**Online Payments API** (Hosted Checkout/Payment Widget), non la Cloud API per lettore fisico (scartata: avrebbe richiesto un lettore posseduto e presente al momento del pagamento, poco adatto alla consegna e comunque più macchinoso da coordinare con lo staff).
- **Contanti**: nessuna integrazione — l'ordine si conferma senza alcun dato di pagamento, si paga in contanti al rider alla consegna.
- **Carta online in anticipo**: al momento della conferma ordine, il cliente viene mandato alla pagina di pagamento ospitata da SumUp (o al widget incorporato nella pagina) — `POST /v0.1/checkouts` crea il checkout con l'importo totale dell'ordine, un `return_url` riceve la notifica di cambio stato. Il webhook di SumUp è **volutamente minimale** (`{event_type, id}`): bisogna sempre rileggere lo stato reale con una `GET /v0.1/checkouts/{id}`, non fidarsi del solo arrivo della notifica.
- **Quali metodi mostrare — interrogati da SumUp, scelti dall'admin** (precisazione dell'utente): SumUp espone `GET /v0.1/checkouts/{id}/payment-methods`, che per ogni checkout restituisce i metodi **davvero disponibili** per quell'account/valuta/importo — non solo carta, ma potenzialmente BANCOMAT Pay, Satispay, Apple Pay, Google Pay, PayPal, e altri metodi non pertinenti in Italia (iDEAL, BLIK, Boleto, P24 — mercati diversi). SumUp stessa consiglia di non mostrarli tutti ciecamente, ma di trattarli come un elenco di ammissibilità. **Flusso proposto**: in Impostazioni (sezione SumUp), un pulsante "Verifica metodi disponibili" interroga l'elenco per l'account collegato e lo presenta come lista di interruttori — l'admin **abilita solo quelli che vuole offrire** ai propri clienti (es. Carta + Satispay, escludendo gli altri irrilevanti), salvati in `Venue.sumupEnabledPaymentMethods` (array di id, es. `["card", "satispay"]`). Al momento del vero checkout, BarManager interseca questa lista con la disponibilità **live** per quel singolo ordine (può variare per importo/valuta) e propone al cliente solo i metodi in entrambi gli elenchi — mai uno scelto dall'admin ma non davvero disponibile in quel momento, né uno disponibile ma non scelto dall'admin. Un metodo appena introdotto da SumUp non compare finché l'admin non rilancia la verifica e lo abilita esplicitamente.
- **Rimborso automatico se un ordine pagato viene rifiutato**: alla transizione a `REJECTED` di un `OnlineOrder` con `paymentStatus = PAID`, BarManager richiama `POST /v0.1/me/refund/{txn_id}` (rimborso pieno, corpo vuoto — l'API supporta anche il parziale, non necessario qui) — `txn_id` ottenuto dalla stessa `GET /v0.1/checkouts/{id}` usata per confermare il pagamento. Il rifiuto di un ordine non deve mai lasciare un cliente addebitato senza che l'ordine venga preparato.
- **Costo**: le commissioni SumUp per un pagamento a distanza/online (Italia, 2026) sono **2,50% flat** — sensibilmente più alte del 0,95%/1,99% di un pagamento con lettore fisico in presenza, un costo che il locale sostiene per ogni ordine pagato con carta online (da tenere presente nel margine, non solo come dettaglio tecnico).
- **Aspetto fiscale IT**: SumUp è un fornitore estero (P.IVA irlandese) — chi ha partita IVA italiana (anche regime forfettario) deve autofatturarsi elettronicamente il servizio acquistato, un adempimento contabile del locale, non qualcosa che BarManager gestisce nell'integrazione.
- **Multi-tenant**: ogni locale ha le proprie credenziali SumUp (account business con P.IVA italiana, API key creata dal proprio Dashboard SumUp → Developer Settings), sullo stesso schema già usato per il token Loyverse (`encryptSecret`/`decryptSecret` di `common/crypto/secret-crypto.ts`, mai in chiaro) — nuovi campi `Venue.sumupEnabled`/`sumupApiKeyEnc`. C'è un **ambiente sandbox** SumUp (account merchant di test, nessun soldo reale, un importo di 11 fallisce sempre di proposito) da usare per collaudare l'integrazione prima del rilascio.

**Ritiro in negozio: pagamento deciso dall'operatore, non dal cliente al checkout** — nuova precisazione dell'utente: nel checkout `/ordina` per il ritiro **non c'è alcuna scelta di pagamento**, né tanto meno un checkout SumUp — il cliente si limita a confermare l'ordine. È **l'operatore**, quando il cliente si presenta fisicamente in negozio a ritirarlo, a decidere e incassare come preferisce (contanti o carta, con il proprio terminale/lettore abituale, del tutto **indipendente** dall'integrazione SumUp qui descritta — quella resta un fatto interno al locale, fuori da BarManager). Solo a quel punto, nella schermata di completamento dell'ordine (`READY`→`COMPLETED`), lo staff seleziona a mano il metodo con cui è stato effettivamente pagato (`paymentMethod`: `CASH`/`CARD_IN_STORE`) — è **questo** l'istante in cui, se la sincronizzazione Loyverse è attiva, viene creata la ricevuta (v. sotto), non prima: per il ritiro l'ordine online è solo una "prenotazione della preparazione", il pagamento vero e proprio resta un fatto di negozio come è sempre stato, prima ancora di questo modulo.
- Esito e riferimenti pagamento su `OnlineOrder`: `paymentMethod` (`CASH`/`CARD_ONLINE`/`CARD_IN_STORE`), `paymentStatus` (`PENDING`/`PAID`/`FAILED`/`REFUNDED`), `sumupCheckoutId`/`sumupTransactionId` (questi ultimi due popolati solo per `CARD_ONLINE`, quindi solo per la consegna).

**Orari e costi di consegna** (nuove impostazioni per locale, sezione "Ordini online" in Impostazioni):
- `Venue.onlineOrdersEnabled` (interruttore generale) + `onlineOrdersPickupEnabled`/`onlineOrdersDeliveryEnabled` (il locale può offrire solo una delle due modalità).
- `Venue.onlineOrdersOpeningHours` (Json, stessa forma di `Venue.openingHours` già usata per menù/prenotazioni, §4): se non impostato usa gli stessi orari di apertura generali, altrimenti li sovrascrive — utile per chiudere la consegna prima della cucina, o per non accettare ordini online certi giorni. Riusa lo stesso util già scritto (`resolveOpeningHours`/`findOpenSlot`), nessuna logica nuova.
- `Venue.deliveryRadiusMeters` (già proposto sopra), `Venue.deliveryFee` (costo fisso), `Venue.deliveryFreeAboveAmount` (consegna gratuita sopra una soglia d'ordine, opzionale) — una tariffa a fasce di distanza resta un'evoluzione successiva (v. §10), non parte di questa v1.
- **Accettazione automatica per fascia da 15 minuti** (nuova precisazione dell'utente) — `Venue.onlineOrdersAutoAcceptEnabled` (interruttore, default `false`) attiva il conteggio automatico degli ordini per fascia di 15 minuti di `requestedAt` (conteggiando gli ordini non rifiutati/annullati già presenti in quella stessa fascia). A differenza della capienza posti delle Prenotazioni (§5.7, che **blocca** del tutto la richiesta oltre soglia salvo tolleranza di overbooking), qui la soglia **non blocca mai** l'invio dell'ordine — la cucina non ha "posti a sedere" fissi, può sempre assorbire un ordine in più, solo con più attesa. Il conteggio decide solo *come* l'ordine parte:
  - se `onlineOrdersAutoAcceptEnabled` è attivo **e** gli ordini già presenti in quella fascia sono sotto la soglia (v. sotto), il nuovo ordine nasce direttamente in `CONFIRMED` (salta `PENDING`): email di conferma immediata al cliente, nessuna azione richiesta allo staff;
  - altrimenti (interruttore disattivato, **oppure** fascia già alla soglia) l'ordine nasce in `PENDING` esattamente come oggi, e resta allo staff decidere accettarlo/rifiutarlo a mano nella coda — la soglia superata è solo un segnale (mostrato in coda, es. "4/3 ordini per le 20:15"), non un rifiuto automatico.
  - **Contatore unico o separato per modalità — scelta dell'admin, non fissa nella specifica** (nuova precisazione dell'utente, risolve la domanda lasciata aperta in §10): `Venue.onlineOrdersAutoAcceptSlotMode` (`COMBINED` | `SEPARATE`). Con `COMBINED` (default) un solo numero, `Venue.onlineOrdersAutoAcceptPerSlot`, vale per ritiro+consegna insieme nella stessa fascia. Con `SEPARATE` due numeri distinti, `Venue.onlineOrdersAutoAcceptPerSlotPickup` e `onlineOrdersAutoAcceptPerSlotDelivery`, ciascuno con il proprio conteggio indipendente per la stessa fascia (utile ad es. per limitare solo le consegne, che assorbono anche il tempo di un rider, senza toccare il ritiro). In Impostazioni un interruttore sceglie la modalità, con solo i campi numerici pertinenti visibili.
- **Proporre un nuovo orario, come per le prenotazioni** (nuova precisazione dell'utente) — stesso meccanismo di `proposeTimeChange`/`confirmTimeChangeByToken` già scritto per le Prenotazioni (§5.7): dalla coda, lo staff può proporre un `OnlineOrder.proposedRequestedAt` diverso (tipicamente per spostare un ordine da una fascia già satura verso una più libera, ma senza alcun vincolo di orario/fascia imposto — è un'azione dello staff, non del widget pubblico), che invia un'email con link alla stessa pagina di tracciamento (`manageToken`) dove il cliente vede un banner e **conferma** (o rifiuta, tornando così a `PENDING` per una nuova proposta/decisione manuale) — nessun cambio effettivo di `requestedAt` finché il cliente non conferma.

**Ciclo di vita e lato staff** — nuova sezione "Ordini online" in amministrazione (coda in tempo reale, stesso `refetchInterval` già usato per lo storico comunicazioni §1-septdecies, non un vero WebSocket in questa v1):
- `OnlineOrderStatus`: `PENDING` (appena arrivato, va accettato/rifiutato come le prenotazioni — oppure saltato del tutto se accettato in automatico, v. sopra) → `CONFIRMED` (in preparazione) → `READY` (pronto per il ritiro, o uscito in consegna) → `COMPLETED` → oppure `REJECTED` (motivo obbligatorio, come `Reservation.rejectionReason`) / `CANCELLED`.
- **Email di stato al cliente**, un nuovo `OnlineOrdersMailService` (stesso pattern di `ReservationsMailService`, §5.7): un'email per transizione rilevante — ricevuto (`PENDING`), confermato (`CONFIRMED`), pronto/in consegna (`READY`), rifiutato con motivo (`REJECTED`) — con link alla pagina di tracciamento (`manageToken`).
- **Notifica allo staff di un nuovo ordine in attesa** — due canali, non uno solo:
  - **Email al locale**: come già per le nuove prenotazioni (§5.7, `sendVenueNotification`), un'email a `Venue.email` ad ogni nuovo `OnlineOrder` in `PENDING`, con riepilogo ordine.
  - **Notifica sonora nell'admin**: la coda "Ordini online" confronta ad ogni poll l'elenco ricevuto con quello precedente e, se compare un nuovo `PENDING` non ancora visto, riproduce un suono (`<audio>`) — da tenere presente che i browser bloccano l'autoplay audio finché l'utente non ha interagito almeno una volta con la pagina, quindi la UI avrà bisogno di un piccolo passo di attivazione esplicita ("Attiva notifiche sonore") al primo caricamento della pagina, non un semplice audio invisibile.
- **Due scontrini distinti alla stampa**, entrambi PDF generati server-side (`PdfService.buildReceiptDocument`, generico a sezioni, già usato per gli ordini fornitori — §5.3) e condivisi con l'app di stampa del sistema via il browser, non una stampa automatica ESC/POS diretta:
  - **Comanda cucina**: solo voci/varianti/modificatori/note per riga — **nessun prezzo, nessun totale, nessun indirizzo**, pensata per restare in cucina/bar dove non deve essere visibile l'importo pagato dal cliente.
  - **Scontrino completo**: dati cliente, modalità (ritiro/consegna) e indirizzo di consegna se presente, ogni riga con prezzo, costo di consegna, totale, metodo e stato del pagamento — pensato per lo staff/il rider, o da allegare alla consegna.
  - Due pulsanti "Stampa" distinti sull'ordine in amministrazione, esattamente come oggi per un solo scontrino ordine fornitore: lo staff sceglie a mano quale stampante fisica riceve quale foglio.
- **Numero di telefono cliente sempre come link `tel:`** su ogni ordine mostrato in amministrazione (coda e storico, v. sotto) — un tocco/clic avvia direttamente la chiamata sul dispositivo dello staff, senza dover copiare il numero a mano.
- **"Naviga" sugli ordini in consegna pronti**: per un `OnlineOrder` con `fulfillment = DELIVERY` in stato `READY`, un pulsante/link apre Google Maps con la destinazione già impostata sulle coordinate di consegna scelte dal cliente sulla mappa (`deliveryLat`/`deliveryLng`), tramite lo schema URL universale `https://www.google.com/maps/dir/?api=1&destination=<lat>,<lng>` (apribile sia da desktop sia da mobile, dove il sistema può proporre di aprirlo nell'app Google Maps installata) — **senza indicare un punto di partenza**: lasciarlo implicito fa usare a Google Maps la posizione attuale di chi clicca (il rider al momento della consegna), che è quasi sempre più corretta della posizione fissa del locale (chi consegna spesso parte già da un altro giro, non dal locale).

**Storico ordini online** — nuova pagina separata dalla coda (stesso schema già adottato per Attività/scadenze, §120: la coda mostra solo gli ordini ancora "vivi" — `PENDING`/`CONFIRMED`/`READY` — mentre lo storico elenca quelli conclusi, `COMPLETED`/`REJECTED`/`CANCELLED`, con filtri per stato/intervallo di date e — coerentemente con quanto sopra — telefono cliente sempre come link `tel:`). Mostra anche l'esito della sincronizzazione Loyverse quando attiva (`loyverseReceiptId`/`loyverseSyncError`, sullo stesso modello già in uso per "Storico ordini" fornitori, §5.3).

**Coerenza con gli standard UI già in uso in BarManager** (promemoria esplicito, da rispettare in fase di implementazione, non solo di specifica): nessuna nuova convenzione grafica per questo modulo, tutte le pagine (impostazioni, coda, storico, checkout pubblico) riusano quanto già stabilito altrove nell'app —
- **Pattern "Aggiungi" in alto a destra con modale** (§73) ovunque serva creare un elemento in amministrazione (es. un tavolo/prodotto già segue questo schema — qui non serve per gli ordini, che nascono solo dal pubblico, ma vale per eventuali entità di supporto come i modificatori);
- **Modello di notifica Toast standard** (§119/§121/§122) per ogni azione admin con esito (accetta/rifiuta ordine, proponi orario, verifica metodi SumUp/Loyverse, ecc.) — mai un semplice `Alert` isolato;
- **`Chip` di stato con etichetta italiana e colore semantico condiviso** (§247) per `OnlineOrderStatus`, sullo stesso schema già in uso per gli stati di prenotazioni/ordini fornitori — non un nuovo set di colori ad hoc;
- **Ogni entità con "Aggiungi" ha anche modifica ed elimina-con-conferma** (§81/§83/§84) — vale per le entità gestite dall'admin (modificatori, mappature metodi di pagamento), non per gli `OnlineOrder` stessi (che si accettano/rifiutano/completano, non si "modificano" come un record CRUD qualsiasi);
- **Paginazione 10/25/50/100 + barra di ricerca** (§204, `CustomersAdmin.tsx`) per la pagina "Storico ordini online", stessa componente riusata, non una nuova implementazione;
- **Colore di accento del tema del locale** (§251-255) su qualsiasi nuovo pulsante/elemento evidenziato, mai un colore hardcoded specifico del modulo;
- **Responsive mobile** (§243-246, niente overflow orizzontale, scroll resettato ad ogni navigazione) fin dalla prima versione delle nuove pagine, non un audit successivo — il checkout pubblico `/ordina` in particolare sarà usato quasi solo da mobile;
- **Padding-top corretto nei modali** (§111/§225, bug già corretto altrove: le label non devono risultare tagliate) in ogni nuovo modale (es. "Proponi nuovo orario", "Accoppia metodo di pagamento").

**Integrazione Loyverse — solo come registro, non come orchestratore** (v. la ricerca discussa sopra in questa conversazione, con fonti): quando `Venue.loyverseIntegrationEnabled` e un nuovo flag esplicito `Venue.loyverseSyncOnlineOrders` (opt-in **separato**, di default `false` — un locale potrebbe non volere ogni ordine online scaricato nel registratore Loyverse, specie durante i test) sono entrambi attivi, alla transizione a `COMPLETED` (non prima: un ordine non ancora concluso non è una vendita reale) BarManager crea una `POST /receipts`. **Per la consegna** il pagamento (`paymentMethod`/`paymentStatus`) è già noto dal checkout, quindi `COMPLETED` può scattare non appena consegnato; **per il ritiro**, come appena descritto, `COMPLETED` scatta solo dopo che l'operatore ha registrato a mano come il cliente ha effettivamente pagato in negozio — è quel valore, non uno presunto, a finire sulla ricevuta. La receipt include:
- `line_items[]` per riga carrello (`variant_id`, quantità, prezzo) + `line_modifiers[]` per i modificatori scelti (`modifier_option_id`, risolto dal mapping Loyverse già mantenuto per item/varianti sincronizzati);
- un solo metodo di pagamento (limite reale dell'API: niente pagamenti split via Loyverse), risolto tramite una **mappatura configurata dall'admin — indipendente e non correlata a quella dei metodi SumUp appena descritta** (precisazione dell'utente: qui non è in gioco quali carte/wallet accetta SumUp, ma solo a quale voce dell'elenco pagamenti **già impostato dal locale in Loyverse** va agganciato ciascun metodo di BarManager). In Loyverse **è il locale stesso** a creare i propri metodi di pagamento nel Back Office, in numero e nomi del tutto liberi — un locale potrebbe avere solo "Contanti"/"Carta", un altro anche "Bancomat" e "Buoni pasto" come voci separate — ciascuno con un proprio `id`: non esiste un metodo fisso "CASH"/"CARD" universale come in BarManager, e `POST /receipts` richiede uno di quegli id specifici dell'account (`GET /payment-types` per leggerli, dati di riferimento da mettere in cache, non da richiedere ad ogni ricevuta). In Impostazioni (sezione Loyverse), un pulsante analogo mostra l'elenco dei metodi di pagamento configurati su Loyverse per quel locale, e per ciascuno dei 3 metodi di BarManager (`CASH`, `CARD_ONLINE` via SumUp, `CARD_IN_STORE` per il ritiro) l'admin **sceglie a quale voce Loyverse corrisponde** (`Venue.loyversePaymentTypeIdCash`/`CardOnline`/`CardInStore`) — es. sia `CASH` che l'eventuale voce "Buoni pasto" resterebbero scelte del locale, non decise da BarManager. Un `OnlineOrder` con un metodo non ancora accoppiato non blocca l'ordine: la sincronizzazione fallisce con un errore leggibile ("metodo di pagamento non collegato a Loyverse"), salvato come le altre.
- **decrementa subito lo stock** e aggiorna la reportistica vendite Loyverse in tempo reale — ma **non genera alcuna comanda cucina né stampa automatica** lato Loyverse: la preparazione/stampa resta interamente gestita da BarManager come sopra, Loyverse riceve solo il risultato finale contabile. Esito (id ricevuta o errore) salvato su `OnlineOrder.loyverseReceiptId`/`loyverseSyncError`, stesso schema di `Order.emailSent`/`emailError` già usato per gli ordini fornitori — un fallimento della sincronizzazione non deve mai bloccare/annullare l'ordine reale con il cliente.

**Cosa resta esplicitamente fuori dal "menù locale"**: nessuno dei campi/flussi sopra (carrello, ritiro/consegna, indirizzo, mappa, stato ordine) tocca la pagina pubblica `/menu` esistente, che rimane un catalogo di sola consultazione — la richiesta di isolare le due modalità è già soddisfatta dal fatto che sono due pagine pubbliche distinte (`/menu` vs `/ordina`) sullo stesso catalogo, non due schermate della stessa pagina con campi condizionali. L'unico punto di contatto è il link in fondo alla pagina descritto sopra, che si limita a rimandare a `/ordina` senza portare nulla della logica di consegna/ritiro dentro `/menu`.

Nota per una futura "ordinazione al tavolo" (già annotata come idea in §6, punto 12): condividerebbe carrello/checkout/`OnlineOrder` con un terzo valore di `OnlineOrderFulfillment` (es. `DINE_IN`, tavolo invece di indirizzo di consegna) — non è parte di questa specifica, ma il modello qui proposto non la precluderebbe.

## 7. Sicurezza, conformità e isolamento multi-tenant

- Password hashate con **argon2id**; JWT access token a vita breve (15 min) + refresh token.
- **RBAC** a livello di endpoint (guard NestJS) e di UI. Il ruolo `SUPER_ADMIN` non ha accesso agli endpoint operativi dei locali (presenze/HACCP/inventario/menù), solo a quelli di gestione `Venue`.
- **Permessi granulari per modulo** (oltre al ruolo): l'Admin di locale può concedere a ciascun dipendente, indipendentemente dal ruolo Dipendente/Responsabile, l'accesso ai moduli HACCP/Inventario/Menù/Attività/Prenotazioni/Clienti (`Employee.allowedModules`, gestito dalla pagina Dipendenti). Verificato lato server ad ogni richiesta da `ModuleAccessGuard` (non solo lato UI); l'Admin non è mai limitato da questo meccanismo. Elenco vuoto = permessi di default del ruolo (Responsabile: HACCP/Inventario/Menù/Attività; Dipendente: solo HACCP) — Prenotazioni e Clienti non compaiono nei default, l'admin li concede esplicitamente.
- **Isolamento tenant**: ogni servizio filtra sempre per `venueId` preso dal JWT, mai da input del client; un tentativo di accedere/modificare una risorsa di un altro `venueId` restituisce 404 (non 403, per non rivelare l'esistenza della risorsa).
- Il login verifica la coerenza fra sotto-dominio da cui si accede e `venueId` dell'utente (eccetto Super Admin, riservato all'host di amministrazione).
- Tutte le scritture su presenze/HACCP/ordini passano da **audit log** immutabile (append-only), scoperto per `venueId`.
- Rate limiting su login e sugli endpoint pubblici (menù, timbratura via QR).
- I QR di timbratura sono legati a un `token` opaco lato server, rigenerabile se compromesso.
- Validazione input con `class-validator` su ogni DTO backend.
- HTTPS obbligatorio in produzione, gestito dal reverse proxy di Portainer/Coolify (certificato wildcard `*.tuodominio.it`).
- Dati HACCP e presenze conservati per il periodo minimo di legge, con export scaricabile in ogni momento.

**Fase 1-ter — Orari di apertura, granularità 15 minuti, cambio orario e durata per prenotazione (completata, §5.7)**
- Backend: `Venue.openingHours` (Json, 7 giorni × fino a 2 fasce ciascuno) sostituisce i vecchi campi fissi `lunchStart/lunchEnd/dinnerStart/dinnerEnd`, con util condivisa (`opening-hours.ts`) usata sia dal menù (§5.4) sia dalle prenotazioni; validazione server-side dell'orario prenotabile per giorno/fascia e ai 15 minuti; flusso proponi/confermi cambio orario (`proposedReservedAt` + email con link di conferma cliente, stesso pattern anti-phishing di Accetta/Rifiuta); durata di occupazione sovrascrivibile per singola prenotazione (`Reservation.slotDurationMinutes`); endpoint di modifica generale (`PATCH /reservations/:id`) per correggere dati/note/durata senza richiedere conferma del cliente.
- Frontend: editor settimanale orari di apertura in Impostazioni locale; widget pubblico `/prenota` aggiornato (riepilogo orari per giorno, avviso se il giorno scelto è chiuso, step del campo orario a 15 minuti); admin Prenotazioni con pulsanti "Cambia orario"/"Modifica"; pagina pubblica di gestione con banner di conferma del nuovo orario proposto.

- **Causa reale del bug dei modali, non quella (sbagliata) individuata nella fase precedente**: nonostante il fix sistematico di `InputLabelProps={{ shrink: true }}` (§ fase 1-duodecies) fosse corretto e necessario, l'etichetta di alcuni campi in cima ai dialoghi restava comunque visivamente tagliata — verificato con screenshot reali (Playwright) dopo la segnalazione dell'utente che il problema persisteva. La vera causa: MUI applica una regola CSS interna, `.MuiDialogTitle-root + .MuiDialogContent-root { padding-top: 0 }`, che **azzera sempre** il padding superiore di `DialogContent` quando segue subito un `DialogTitle` — con una specificità (due classi in combinatore di fratelli adiacenti) più alta di qualunque `sx={{ pt: 4 }}` locale (una sola classe), che quindi non ha **mai** vinto in nessuno dei punti dove era stato aggiunto in buona fede (~18 pagine). Con padding-top realmente a 0, l'etichetta "shrink" di un campo in prima riga — che sporge di ~9px sopra il proprio bordo per design, normalmente assorbiti dal padding — finisce sopra il bordo superiore del contenitore, che è scrollabile (`overflow-y: auto`) e quindi la ritaglia. ## 9. Nota di deployment

### 9.0 Due file compose: produzione vs sviluppo

- `docker-compose.yml` è il file di **produzione**: costruisce lo stage `production` dei Dockerfile (backend compilato con `nest build`, frontend buildato con Vite e servito da Nginx), senza montare il codice sorgente nei container. È questo il file che Portainer/Coolify leggono collegandosi al repository.
- `docker-compose.override.yml` esiste **solo per lo sviluppo in locale**: Docker Compose lo carica automaticamente insieme a `docker-compose.yml` quando lanci `docker compose up` da questa cartella (nessuna opzione da aggiungere), riportando i servizi allo stage `dev` con hot reload e bind mount del codice. Portainer e Coolify, collegandosi al repository Git, non lo considerano affatto: usano solo `docker-compose.yml`.
- La CLI di Prisma (`prisma`) è tenuta come **dipendenza di runtime** (non solo di sviluppo) apposta: serve per eseguire `prisma db push` all'avvio del container anche nell'immagine di produzione, dove le `devDependencies` sono escluse (`npm ci --omit=dev`).

### 9.1 Portainer / Coolify e sotto-domini

- **DNS**: creare un record **wildcard** `*.tuodominio.it → IP del server` (oltre, se serve, ad `admin.tuodominio.it` se si preferisce un sotto-dominio dedicato invece della wildcard per l'host di amministrazione).
- **Coolify** — passi:
  1. *New Resource* → **Docker Compose**, collegando il repository (branch `main`); Coolify legge `docker-compose.yml`.
  2. Impostare le variabili d'ambiente nella sezione *Environment Variables* della risorsa (stesso contenuto di `.env.example`: credenziali Postgres, `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET`, SMTP, `ROOT_DOMAIN`, ...) — Coolify genera da sé il file `.env` che il compose si aspetta (`env_file: .env`).
  3. Assegnare il dominio al servizio **frontend** (porta 80): `*.tuodominio.it` per la wildcard (richiede un provider DNS collegato a Coolify per la validazione **DNS-01**, obbligatoria per i certificati wildcard) oppure un dominio singolo in assenza di wildcard. Il servizio **backend** non va esposto pubblicamente.
  4. Deploy. Il primo avvio applica lo schema con `prisma db push`; creare l'utente iniziale con `docker compose exec backend npm run prisma:seed` (terminale Coolify o SSH) e cambiare subito le password di default (`backend/prisma/seed.ts`).
- **Portainer**: si importa `docker-compose.yml` come stack (Stacks → Add stack → Repository); se davanti c'è Traefik o Nginx Proxy Manager, va aggiunta a mano la regola di routing per `*.tuodominio.it` verso il servizio `frontend` (porta 80) — un esempio di label Traefik è incluso, commentato, in `docker-compose.yml`.
- L'app **non** include un proprio container reverse proxy: il traffico arriva già in chiaro (HTTP) dal proxy della piattaforma al container `frontend`, che fa da unico punto d'ingresso (proxando `/api` e `/uploads` al backend).

### 9.2 Stampanti di rete

La stampa (report HACCP, checklist ordini, test da Impostazioni) non parte dal server: il backend prepara solo il contenuto testuale (`PrintingService.buildTestJob`/`buildReportJob`, che restituiscono `{title, lines, footer}`) e il **browser** lo stampa con la stampa standard del sistema operativo (`window.print()` su un iframe nascosto, formattato a larghezza scontrino — `frontend/src/printing/printJob.ts`).

Il motivo di questa scelta: nessuna libreria browser può aprire una connessione diretta (TCP) verso una stampante di rete — è un limite di sicurezza della piattaforma web, non risolvibile lato codice (verificato anche con librerie dedicate come QZ Tray, receipt.js/receiptjs, `@point-of-sale/*`: tutte richiedono comunque un componente esterno — un helper desktop, o l'app "print service" del sistema operativo — per il salto finale sulla rete). Da qui la scelta di appoggiarsi al sistema di stampa del dispositivo:

- **Windows/macOS/Linux**: la stampante va configurata come stampante di sistema (driver, o via IP se il sistema lo supporta); il dialogo di stampa la mostra tra le opzioni.
- **Android**: va installata una volta un'app che fa da "print service" e sa parlare ESC/POS in rete, es. [RawBT](https://play.google.com/store/apps/details?id=ru.a402d.rawbtprinter) (gratuita): una volta installata compare come stampante nel dialogo di stampa standard di Android (quindi anche da Chrome/WebView), e consegna il contenuto alla stampante via WiFi/LAN, Bluetooth o USB.
- **iOS**: nessuna soluzione altrettanto generica; funziona solo con stampanti realmente certificate AirPrint (alcuni modelli Star Micronics).
- Questo funziona a prescindere da dove sia ospitato il backend (on-premise o cloud): il dialogo di stampa e la consegna avvengono sempre sul dispositivo/rete di chi stampa, non sul server.
- Limite noto: non essendo stampa ESC/POS raw, si perdono i comandi di formattazione diretta (grassetto, taglio automatico della carta) — si stampa una pagina HTML semplice, e non c'è modo per il browser di sapere se l'utente ha davvero confermato la stampa dal dialogo (si considera "stampato" non appena il dialogo si apre).
- Se in futuro serve tornare a stampa ESC/POS raw pilotata dal server (bordi/tagli, nessun dialogo, ma richiede un helper installato): QZ Tray per desktop resta un'opzione valida (non per Android, dove non esiste), oppure — visto che il progetto prevede già un wrapper Capacitor per Android (v. sopra) — un plugin nativo Capacitor con socket TCP diretto (es. libreria Android `DantSu/ESCPOS-ThermalPrinter-Android`, con wrapper `capacitor-thermal-printer`), che stampa in silenzio senza dialogo né app di terze parti.

## 10. Decisioni ancora aperte (da confermare con l'utente)

- Dominio principale da usare per la wildcard (es. `tuodominio.it`) e provider DNS (necessario per il certificato wildcard via DNS-01 su Coolify).
- Host riservato al Super Admin: sotto-dominio dedicato (`admin.tuodominio.it`) o dominio apice.
- Storage delle foto del menù: volume Docker locale (default attuale, più semplice) oppure S3/MinIO fin da subito, se si prevede un deploy multi-host senza volumi condivisi.

- Provider SMTP: globale di piattaforma (un solo mittente per tutti i locali) oppure configurabile per singolo locale.

- **Prenotazioni (§5.7)** — implementata in v1 con queste scelte di default (da confermare/rivedere con l'utente):

Resta da capire se un locale userà davvero il turnover (più prenotazioni sullo stesso tavolo in orari diversi dello stesso servizio) o preferisce "un turno = tutto il servizio" (in tal caso basta impostare una durata pari all'intero servizio).

  - ~~**Sincronizzazione Loyverse — quando creare la ricevuta**~~ — **risolto**: alla chiusura effettiva dell'ordine (`COMPLETED`), non alla sola conferma (`CONFIRMED`) — un ordine non ancora concluso non è una vendita reale, nonostante il ritardo rispetto al momento della conferma. Sempre opt-in separato (`Venue.loyverseSyncOnlineOrders`, di default `false`), un venue può decidere di non volerla affatto. ~~Quale `payment_type_id` Loyverse usare per quel metodo~~ — **risolto**: mappatura configurata dall'admin in Impostazioni, che accoppia `CASH`/`CARD_ONLINE`/`CARD_IN_STORE` ai `payment_type_id` letti da `GET /payment-types` del proprio account (`Venue.loyversePaymentTypeIdCash`/`CardOnline`/`CardInStore`); un metodo non accoppiato fa fallire la sola sincronizzazione (errore in `loyverseSyncError`), non l'ordine — v. §5.10.
  - ~~**Modificatori — necessari fin dal v1?**~~ — **risolto**: sì, implementati fin dalla prima versione insieme al resto del modulo (`MenuModifierGroup`/`MenuModifierOption`/`MenuItemModifierGroup`, funzionanti anche senza Loyverse, come già le Varianti, §88) — non rimandati a una fase successiva.
  - ~~**Zona di consegna e costo — fissa+soglia o a fasce di distanza?**~~ — **risolto**: fissa+soglia, come proposto — raggio massimo in metri (`Venue.deliveryRadiusMeters`, illimitato se non impostato), costo fisso (`Venue.deliveryFee`) e soglia di consegna gratuita (`Venue.deliveryFreeAboveAmount`). Una tariffa a fasce di distanza resta un'eventuale evoluzione futura, fuori da questa v1.
  - ~~**Contatori cliente**: proposti `Customer.firstOrderAt`/`lastOrderAt`/`ordersCount` paralleli agli equivalenti di prenotazione già esistenti — da confermare se preferibile un contatore unico invece di due paralleli, e se la UI deve mostrare entrambi i conteggi~~ — **risolto**: contatori paralleli confermati, più un nuovo `totalOrdersSpent` (spesa totale, aggiornato in incremento ad ogni ordine `COMPLETED`); `CustomersAdmin.tsx` mostra entrambi come colonne proprie ("Ordini online" e "Spesa totale"), accanto a "Prenotazioni" già esistente — v. §5.10.
  - ~~**Riuso di `Venue.gpsLat/gpsLng` come punto di partenza della consegna**~~ — **risolto**: sì, si riusa lo stesso campo (oggi pensato per il raggio di timbratura, §5.1) invece di duplicare le coordinate del locale in un secondo campo — la posizione del locale è unica, usata sia per la geofence dipendenti che per la distanza di consegna.
  - ~~**Capacità per fascia da 15 minuti**: proposta come un unico contatore per fascia che somma ritiro **e** consegna insieme — da confermare che non serva invece un contatore distinto per modalità~~ — **risolto**: scelta dell'admin in Impostazioni (`Venue.onlineOrdersAutoAcceptSlotMode`, `COMBINED` con un solo contatore condiviso o `SEPARATE` con due contatori indipendenti per ritiro/consegna) — v. §5.10.
